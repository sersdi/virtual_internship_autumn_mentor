У клиента возникла проблема с установкой программы на прод среду.
Проблема заключается в том, что перед запуском программы нужно
создать базу данных и запустить скрипты для создания структуры
и заполнения таблиц начальными значениями. Клиент создал
базу данных, но забыл выполнить SQL скрипты. При запуске приложение
упало с ошибкой.

Клиент интересуется, можно ли сделать так, чтобы скрипты по
созданию структуры базы данных и заполнению таблиц начальными
значениями выполнялись приложением автоматически при запуске,
чтобы не надо было их отдельно руками запускать.

Добавил в приложение поддержку Liquibase.
Изменения коснулись следующих файлов:
/build.gradle
/src/main/resources/application.properties
/src/test/resources/application.properties
/src/main/resources/db/changelog/*

Задача:
Изучить Liquibase.
Провести эксперимент: удалить базу данных, создать пустую базу
данных с таким же названием, без создания структуры таблиц
запустить приложение, изучить что произойдёт с базой данных,
объяснить как это произошло и почему. Выключить приложение,
включить его повторно и убедиться, что оно не упадёт и для таблиц
в базе данных не будут созданы дубликаты, объяснить почему.

Решение:

Liquibase не создаёт дубликаты при повторном запуске,
    потому что ведёт журнал уже выполненных изменений и на его основе решает,
    какие скрипты применять, а какие пропустить.

Таблица DATABASECHANGELOG
При первом запуске Liquibase автоматически создаёт в целевой БД специальную таблицу DATABASECHANGELOG.
В ней хранится список всех применённых changeSet’ов (блоков изменений).
В каждой строке — идентификаторы changeSet: id, author, а также хеш содержимого changeSet.

Уникальность changeSet по комбинации (id, author)
Каждый changeSet должен иметь уникальный id и author.
Именно по этой паре Liquibase определяет, был ли changeSet уже применён.
Если запись с такой парой есть в DATABASECHANGELOG,
    changeSet повторно не выполняется.

Контроль целостности через MD5-хеш
Для каждого changeSet Liquibase вычисляет MD5-хеш от содержимого.
При повторном запуске он сравнивает текущий хеш с тем, что записан в DATABASECHANGELOG.
Если кто-то поменял SQL внутри changeSet, хеши не совпадут—Liquibase
    либо откажется применять (в зависимости от настроек),
    либо пометит как изменённый. Это защищает от незаметных правок,
    которые могли бы привести к некорректным состояниям.

Идемпотентность скриптов (дополнительная страховка)
Хотя основной механизм — журнал, сами скрипты часто делают идемпотентными:
    используют CREATE TABLE IF NOT EXISTS, проверяют существование объектов,
    делают условное выполнение.
Это хорошая практика, но не обязательное требование Liquibase:
    основная гарантия отсутствия дублей — именно таблица лога.
