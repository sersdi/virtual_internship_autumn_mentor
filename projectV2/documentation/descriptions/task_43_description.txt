Узнал больше про CI процесс.
Суть в том, чтобы автоматизировать рутину: после каждого изменения кода система сама проверяет, всё ли в порядке.

Триггер.
Всё начинается с события.
В YAML-файле (он лежит в папке .github/workflows) вы указываете, что должно запустить пайплайн.
Например: пуш в ветку main, создание или обновление Pull Request, расписание.
Как только событие происходит, GitHub «замечает» это и готовится запустить рабочий процесс.

Чтение конфигурации.
GitHub смотрит на YAML-файл.
В нём описаны jobs (задания) и steps (шаги внутри заданий).
Система строит план: в каком порядке что выполнять, есть ли зависимости между заданиями.

Выделение раннера.
Для каждого задания GitHub подбирает виртуальный сервер (runner).
Важно: каждое задание обычно запускается в изолированной среде — у него свой чистый экземпляр.
Это гарантирует, что настройки или файлы из одного теста не помешают другому.

Выполнение шагов.
Раннер приступает к делу. Типичная цепочка для проекта может выглядеть так:
    Checkout. Код из репозитория копируется на раннер.
    Настройка среды. Устанавливаются нужные инструменты: язык программирования, менеджер пакетов (npm, pip, maven), конкретные версии зависимостей.
    Установка зависимостей. Запускаются команды вроде npm install или pip install -r requirements.txt, чтобы подтянуть все библиотеки, от которых зависит проект.
    Сборка. Если проект требует компиляции или сборки (например, из исходного кода в бинарный файл или в бандл для веба), этот шаг тоже автоматизирован.
    Тестирование. Запускаются автоматические тесты: юнит-тесты, интеграционные, иногда линтеры (проверяют стиль кода).
    Дополнительные шаги. Иногда добавляют сохранение артефактов (например, собранного JAR-файла или Docker-образа), чтобы их можно было использовать в следующих заданиях или для деплоя.
    Анализ результатов. После каждого шага система смотрит на результат. Если какой-то тест упал или команда завершилась с ошибкой — пайплайн останавливается (или можно настроить, чтобы он продолжал проверять остальное, но итоговый статус будет «неуспех»).
    Отчёт. Вы видите результат в интерфейсе GitHub (вкладка Actions). Там отображается лог каждого шага: что было сделано, где возникла ошибка, сколько времени заняло.

Несколько нюансов, которые стоит знать
Матрица (Matrix).
Часто нужно проверить код в разных условиях: на разных версиях языка, ОС, с разными настройками.
Для этого используют матрицу: одно задание разворачивается в несколько, каждое со своей комбинацией параметров.

Секреты (Secrets).
В коде или в настройках часто встречаются чувствительные данные (пароли, токены).
В GitHub их хранят отдельно как Secrets и подставляют в шаги пайплайна при выполнении.
Зависимости между заданиями. Можно настроить, чтобы одно задание запускалось только после успешного завершения другого. Например, сначала тесты, а если они прошли — сборка и деплой.
