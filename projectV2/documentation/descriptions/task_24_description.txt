IoC в действительности поддерживает три
способа получения внешних зависимостей классом:
- через конструктор;
- через set метод;
- через свойство объекта.

-Внедрение зависимостей через конструктор (Constructor Injection).
Это базовый и наиболее предпочтительный способ реализации принципа инверсии управления (IoC).
При таком подходе зависимости, необходимые для работы класса, передаются ему в качестве параметров при создании экземпляра.
Управление созданием объектов и их зависимостей делегируется внешнему контейнеру IoC.
Пример:
    public class UserService {
        private final UserRepository repository;

        // Конструктор с зависимостями
        public UserService(UserRepository repository) {
            this.repository = repository;
        }

        // Бизнес-логика
    }

-Внедрение зависимости через set метод.
Вместо того чтобы объект сам создавал свою зависимость (например, через new),
    он получает её извне — через специальный метод (сеттер),
    а управляет всем этим внешним миром (созданием объектов, их связыванием) специальный компонент — IoC-контейнер
Пример:
    public class Car {
        private Engine engine;

        // Сеттер для инъекции зависимости
        public void setEngine(Engine engine) {
            this.engine = engine;
        }
    }

-Внедрение зависимости через св-во объекта.
Суть в том, что объект объявляет публичное свойство,
    в которое извне передаётся зависимость (например, сервис, репозиторий или логгер).
    А уже внешний контейнер (или другой компонент) «подставляет» в это свойство нужный экземпляр при создании объекта.
Пример:
    public class UserService
    {
        // Свойство, через которое извне внедряется зависимость
        public IUserRepository Dependency { get; set; }

        public void SaveUser(User user)
        {
            // Используем Dependency здесь
            repository.Save(user);
        }
    }

    // Где-то в другом месте код создаёт и настраивает объект
    var service = new UserService();
    service.Dependency = repository; // Внедряем зависимость
    service.SaveUser(user);

Плюсы и минусы внедрения зависимостей.
-Внедрение через конструктор
Плюсы:
    Явная обязательность. Сразу видно, без какой зависимости класс не сможет создаться.
    Иммутабельность. Зависимости задаются при создании объекта и обычно сохраняются в final-полях, что делает объект неизменяемым.
    Упрощённое тестирование. Легко подставлять моки или стабы для обязательных зависимостей в юнит-тестах, не запуская весь контейнер.
    Снижение риска циклических зависимостей. Поскольку объект создаётся полностью готовым, контейнер может строже контролировать инициализацию.
Минусы:
    Громоздкий конструктор. Если у класса много зависимостей, сигнатура конструктора становится длинной, что может ухудшить читаемость кода.
    Сложность при большом количестве опциональных зависимостей. В таких случаях лучше использовать другие подходы.
Когда использовать: для обязательных зависимостей, без которых класс не имеет смысла (например, репозиторий для работы с данными).

-Внедрение через сеттер (установщик)
Плюсы:
    Гибкость. Позволяет задать зависимость после создания объекта, что удобно для опциональных или динамически меняемых зависимостей.
Минусы:
    Риск неполной инициализации. Если сеттер не вызван для обязательной зависимости, объект может оказаться в несогласованном состоянии.
    Сложность тестирования. Не всегда удобно подставлять моки для таких зависимостей в юнит-тестах.
    Нарушение принципа единственной ответственности. Класс начинает «знать» о том, как его настраивает внешний контейнер, что может усложнить рефакторинг.
Когда использовать: для необязательных зависимостей (например, логгер), а также в случаях, когда требуется сложная или отложенная настройка.

-Внедрение через поля (свойства)
Плюсы:
    Лаконичность кода. Меньше шаблонного кода для внедрения.
Минусы:
    Нарушение инкапсуляции. Прямое внедрение в поля нарушает принцип инкапсуляции.
    Риск полурабочего состояния. Объект можно создать через конструктор по умолчанию без зависимостей, а затем вызвать сеттер позже — в этот момент зависимость может быть null, что приведёт к NullPointerException.
    Сложность тестирования. Сложно подставлять моки для таких зависимостей в юнит-тестах.
    Скрытые зависимости. Класс начинает «скрывать» свои истинные зависимости, так как доступ к ним осуществляется через поле, а не через явный интерфейс.
Когда использовать: крайне редко и с большой осторожностью, только если зависимость действительно опциональна и есть разумное значение по умолчанию.
