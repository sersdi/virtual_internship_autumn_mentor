Узнаю подробнее про протокол HTTP, а именно:
    - типы запросов (GET/POST/PUT/DELETE);
    - формат URL строки;
    - параметры которые можно указывать в URL строке;
    - тело (body) запроса и какую информацию там можно передавать.

HTTP: суть и ключевые механизмы
HTTP (HyperText Transfer Protocol)—это протокол прикладного уровня для передачи данных в интернете.
Он лежит в основе работы веба: по нему браузеры запрашивают страницы, API обмениваются данными, а клиенты получают файлы.

Модель «запрос‑ответ» и роль в сетевой архитектуре
HTTP работает по модели «клиент — сервер»:

Клиент (браузер, curl, Java‑клиент) отправляет запрос.
Сервер (Nginx, Apache, Spring Boot‑приложение) обрабатывает его и возвращает ответ.
HTTP находится на прикладном уровне (верхний уровень стека TCP/IP).
Он использует TCP как транспорт (надёжная доставка, порядок пакетов), а поверх TCP уже работает HTTP.
Стандартный порт—80, для защищённой версии HTTPS—443.

Важная особенность: HTTP stateless (без сохранения состояния). Сервер не обязан помнить предыдущие запросы. Состояние (корзина, авторизация) реализуют отдельно — через cookies, токены, сессии.

Основные HTTP‑методы
    GET - запросить ресурс. Безопасный и идемпотентный: не должен менять состояние сервера.
    POST - отправить данные на сервер, часто для создания ресурса или отправки формы.
    PUT - полностью заменить ресурс по указанному URI.
    PATCH — частично обновить ресурс.
    DELETE - удалить ресурс.
    HEAD - как GET, но возвращает только заголовки (без тела). Удобно для проверки метаданных.
    OPTIONS - узнать, какие методы поддерживает сервер для данного URI.

Идемпотентный метод: многократный вызов даёт тот же эффект, что и однократный (GET, PUT, DELETE).
Безопасный метод: не меняет состояние сервера (GET, HEAD).

URL (Uniform Resource Locator)— это адрес ресурса в сети (страницы, файла, API‑эндпоинта и т.п.).
Он позволяет однозначно указать, где находится ресурс и как к нему обратиться.
Формат URL стандартизирован в RFC 3986.

Общая структура URL
Формат URL можно представить так:
схема://[логин[:пароль]@]хост[:порт][/путь][?запросы][#якорь]

Схема (протокол)
Это начало адреса, которое говорит, по какому протоколу обращаться к ресурсу.
Примеры: http, https, ftp, mailto, file.

В HTTP/HTTPS это определяет, как именно будет устанавливаться соединение и передаваться данные.
Схема задаёт «тип взаимодействия», а дальше уже работают нижележащие уровни (TCP/IP и т.д.).
Хост (домен или IP)
Указывает, на какой сервер идти. Это может быть:

доменное имя: example.com;
IP‑адрес: 192.0.2.1.
Хост нужен, чтобы DNS мог превратить имя в IP, а затем TCP/IP доставить пакеты.

Порт (необязательно)
Номер порта, на котором слушает сервис. Если не указан, используется порт по умолчанию:
HTTP— 80;
HTTPS— 443.
Пример: example.com:8080-сервер на нестандартном порту.

Путь
Определяет конкретный ресурс на сервере.
Например:
    /products—каталог товаров;
    /products/shoes/nike-air —конкретная страница.
Путь может быть пустым (тогда подразумевается «главная страница»).

Запросы (query string)
Часть после ?, содержит параметры в формате ключ=значение, пары разделяются &.
Пример:
    ?category=shoes&color=black&page=2
Такие параметры часто используют:
    -для поиска и фильтров;
    -передачи данных в API;
    -аналитики (UTM‑метки).
В бэкенде эти параметры обычно парсят и используют для формирования ответа (фильтрация списка, пагинация и т.п.).

Якорь (фрагмент)
Часть после #. Она не отправляется на сервер, а обрабатывается браузером.
Пример:
    https://example.com/docs#installation
Браузер откроет страницу и прокрутит к элементу с id="installation".

Логин и пароль (редко используется)
Форма user:pass@host формально поддерживается, но в современных веб‑проектах почти не применяется из‑за безопасности.

Примеры URL и разбор

https://example.com
схема: https;
хост: example.com;
порт: по умолчанию 443;
остальные части отсутствуют.

http://localhost:8080/api/users?id=123#profile
схема: http;
хост: localhost;
порт: 8080;
путь: /api/users;
запрос: ?id=123;
якорь: #profile.

ftp://user:secret@files.example.com/downloads/file.zip
схема: ftp;
логин/пароль: user:secret;
хост: files.example.com;
путь: /downloads/file.zip.

Кодирование URL (URL encoding / percent‑encoding)
URL поддерживает ограниченный набор символов. Всё, что не входит в «безопасный» набор, кодируется как %XX (шестнадцатеричный код байта).
Примеры:
    пробел → %20 (или иногда + в query string);
    кириллица → сначала в UTF‑8, затем каждый байт как %XX. Например, кофе превратится в длинную последовательность процентов.
    спецсимволы: /, ?, # имеют особое значение, поэтому если их нужно передать как часть значения, их тоже кодируют.
В Java это делают методами вроде URLEncoder.encode() (для query) или более низкоуровневыми средствами для полного контроля.

Абсолютные и относительные URL
Абсолютный URL содержит всё: схему, хост и т.д.
Пример:
    https://example.com/blog/post-1. Его можно использовать где угодно.
Относительный URL задаётся относительно текущего документа.
Примеры:
    /blog/post-1 — относительно корня сайта;
    post-1.html — относительно текущей папки;
    ../other/page.html — подъём на уровень вверх.
Относительные URL удобны в HTML и в коде, когда базовый адрес уже известен.

Статические и динамические URL
Статические: фиксированный путь, обычно без query‑параметров.
Пример: /products/nike-air. Часто делают «человекопонятными» для SEO и удобства.

Динамические: содержат параметры, которые формируют контент на лету.
Пример: /products?id=123&sort=price. Часто встречаются в старых или простых CMS и в API.

Важные нюансы
Регистр: схема и хост обычно считаются регистронезависимыми, но путь и query—регистрозависимы.
То есть Example.com и example.com — это один хост, а /Page и /page могут вести на разные ресурсы.

Длина URL: формально нет жёсткого лимита, но браузеры и серверы могут ограничивать длину (часто около 2000символов).
Длинные query‑строки признак того, что лучше использовать POST‑запросы или другой дизайн API.
IRI vs URL: IRI (Internationalized Resource Identifier) позволяет использовать Unicode напрямую (например, кириллицу в домене), но при передаче по сети всё равно преобразуется в совместимый формат.

    Параметры в URL‑строке (query parameters)
Параметры в URL идут после знака ? и имеют формат ключ=значение, пары разделяются символом &.
Пример:
    https://example.com/search?q=кофе&lang=ru&page=2&sort=price_asc
    Здесь параметры: q, lang, page, sort.

Какие параметры можно указывать?
Практически любые, если это предусмотрено API или веб‑приложением.
Типичные категории:
    Фильтрация: category=shoes, brand=nike, color=black.
    Пагинация: page=3, limit=20, offset=40.
    Сортировка: sort=price_asc, sort=date_desc.
    Поиск: q=java tutorial.
    Локализация/настройка отображения: lang=en, format=json, timezone=Europe/Moscow.
    Аналитика (UTM‑метки): utm_source=google, utm_campaign=summer_sale.
    Идентификаторы сессий/токенов (не рекомендуется для чувствительных данных): session_id=abc123.
Важные ограничения и нюансы:
    -Длина URL.
Браузеры и прокси обычно ограничивают длину URL примерно 2000символами.
Если параметров много или значения длинные—лучше переносить данные в тело запроса.
    -Безопасность.
Параметры URL видны в адресной строке, сохраняются в истории браузера, логах сервера и могут попадать в рефереры.
Не передавайте пароли, токены доступа, персональные данные в query‑параметрах.
    -Кодирование.
Специальные символы и не‑ASCII (например, кириллица) нужно кодировать через percent‑encoding: кофе → %D0%BA%D0%BE%D1%84%D0%B5.
В Java для этого используют URLEncoder.encode().
    -Семантика HTTP.
По стандартам GET‑запросы должны быть безопасными и идемпотентными: они запрашивают данные, а не меняют состояние сервера.
Поэтому параметры в URL чаще используют для выборки, фильтрации, пагинации.
Парсить query‑параметры можно вручную (разбивка по ?, &, =), но в реальных проектах используют библиотеки (Spring MVC, JAX‑RS) или классы вроде URI + самописный парсер.

Тело (body) запроса: что и как там передают.
Тело запроса — это часть HTTP‑сообщения после заголовков, отделённая пустой строкой.
Оно есть не у всех методов: например, у GET и HEAD тело обычно отсутствует, а у POST, PUT, PATCH — почти всегда есть.

В каких методах используют body
    POST — создание ресурса, отправка форм, загрузка файлов.
    PUT — полная замена ресурса.
    PATCH — частичное обновление.
    Реже: DELETE с деталями, кастомные методы.

Форматы данных в body
Чаще всего используют такие форматы:
    application/x‑www‑form‑urlencoded — классические HTML‑формы. Данные в виде key1=value1&key2=value2. Кириллица и спецсимволы кодируются. Подходит для простых пар «ключ‑значение».
    multipart/form‑data — для загрузки файлов и смешанных данных (файлы + текстовые поля). Часто используют в веб‑формах.
    application/json — самый популярный формат для API.
    Пример:
        json
        {
          "name": "Иван",
          "age": 30,
          "tags": ["java", "http"],
          "active": true
        }
application/xml—реже, но встречается в старых и корпоративных системах.
Сырые данные: бинарные файлы, изображения, архивы—тип application/octet-stream или конкретный MIME (например, image/png).
Тип данных обязательно указывают в заголовке Content-Type.

Какую информацию можно передавать в body
Структурированные данные: JSON/XML с объектами, списками, вложенными структурами.
Файлы: изображения, документы, архивы.
Большие текстовые данные: логи, отчёты, CSV/TSV.
Бинарные данные: сериализованные объекты, зашифрованные блоки, медиа.
Конфиденциальные данные: пароли, токены, ПДН — но только по HTTPS.
В отличие от URL‑параметров, тело не ограничено длиной URL и не видно в адресной строке. Но без HTTPS трафик всё равно можно перехватить, поэтому шифрование обязательно для чувствительных данных.

Практические примеры для Java
Отправка JSON в body (современный подход)
java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;

public class Main {
    public static void main(String[] args) throws Exception {
        String json = """
            {
              "name": "Кофе Арабика",
              "price": 1200,
              "tags": ["premium", "organic"]
            }
            """;

        HttpClient client = HttpClient.newHttpClient();
        HttpRequest request = HttpRequest.newBuilder()
            .uri(URI.create("https://api.example.com/products"))
            .header("Content-Type", "application/json")
            .POST(HttpRequest.BodyPublishers.ofString(json))
            .build();

        HttpResponse<String> response = client.send(request, HttpResponse.BodyHandlers.ofString());
        System.out.println(response.statusCode());
        System.out.println(response.body());
    }
}
Отправка формы (x‑www‑form‑urlencoded)
java
String form = "username=ivan&password=secret&lang=ru";
HttpRequest request = HttpRequest.newBuilder()
    .uri(URI.create("https://api.example.com/login"))
    .header("Content-Type", "application/x-www-form-urlencoded")
    .POST(HttpRequest.BodyPublishers.ofString(form))
    .build();
