Пример **легенды для интервью Java Backend разработчика**,
которая демонстрирует умение проектировать **уровень бизнес-логики**
с использованием **Spring**, **IoC (DI)**, компонентов,
подсистем и принципов архитектурного разделения:

🔹 **Контекст проекта**
В рамках одного из проектов мы разрабатывали внутреннюю
платформу для управления страховыми продуктами. Приложение
было построено на **Spring Boot**, с четким разделением слоев:
контроллеры, слой бизнес-логики, слой доступа к данным,
интеграции с внешними системами.

🔹 **Моя зона ответственности**
Я участвовал в проектировании и реализации **бизнес-логики приложения**
— "сердца" всей системы. Это включало в себя:

### ✅ Архитектура бизнес-слоя

* Разделение бизнес-логику на **модули и подсистемы**,
соответствующие ключевым предметным областям:
`Policy`, `Customer`, `Payments`, `Claims`, 'Underwriting'.

* Для каждой подсистемы была разработана четкая **domain package structure**.


### ✅ Использование Spring и IoC

* Все бизнес-сервисы были реализованы через **`@Service`** и внедрялись с помощью **встроенного DI-контейнера Spring** (`@Autowired`, `@RequiredArgsConstructor`).
* Я активно использовал **интерфейсы для абстракций**, чтобы при необходимости можно было легко заменить реализацию (например, подменить репозиторий на мок в тестах или интеграцию на другую систему).
* В некоторых случаях применял **`@Qualifier`** и **`@Primary`** для управления внедрением различных реализаций одного интерфейса.

### ✅ Принципы SOLID и IoC

* Разделял классы по **принципу единственной ответственности (SRP)**:

  * Один класс — одна задача: `PaymentCalculator`, `RiskAssessor`, `PolicyValidator`.
* Не допускал смешения бизнес-логики с контроллерами или DAO.
* Ввёл **сервисы-координаторы** (Application Service), которые оркестрируют вызовы компонентов, а не содержат логику сами.

### ✅ Валидация и безопасность бизнес-операций

* Все входящие данные проходили проверку на уровне DTO (`@Validated`) и повторную — на уровне бизнес-логики.
* Для обеспечения безопасности и ограничений я использовал **принцип "защищённых команд"** — каждая операция (например, "отменить полис") шла через строгую проверку: можно ли выполнять, кто исполняет, в каком состоянии находится объект.

### ✅ Тестируемость и расширяемость

* Бизнес-сервис писался **с явной зависимостью только от интерфейсов** (`PolicyRepository`, `PaymentGatewayClient`), благодаря чему он был **легко покрываем unit-тестами**.
* Все операции моделировались как **domain-ориентированные use cases**, например:

  ```java
  policyService.cancelPolicy(policyId, userContext);
  paymentService.recalculatePremium(policyId);
  ```

🔹 **Достижения**

* Повысил читаемость и сопровождаемость кода: бизнес-правила были выделены в отдельные сервисы, легко читаемые даже не-технарями.
* Упростил тестирование бизнес-логики: unit-тесты запускались за миллисекунды и не требовали Spring-контекста.
* Сократил дублирование и технический долг за счёт выделения повторяющихся логик в общие бизнес-компоненты (`BaseValidator`, `MoneyRoundingService` и т.д.)

🔹 **Технологии**

* Spring Boot 3, Spring Context (IoC), Spring Validation
* Lombok, MapStruct
* Java 21+, JUnit 5, Mockito
* PostgreSQL, Spring Data JPA
* Архитектура: Hexagonal / Layered, DTO → Domain → Persistence
