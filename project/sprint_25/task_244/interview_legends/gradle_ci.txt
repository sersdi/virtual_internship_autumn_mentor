Пример **легенды для интервью Java Backend разработчика**,
в которой он рассказывает, **как и зачем использовал Gradle
и CI (Continuous Integration)** в своей работе:

🔹 **Контекст проекта**
В одном из проектов я работал над разработкой микросервисов
для внутренней платформы автоматизации документооборота.
Команда была распределённой, и мы активно использовали **GitLab**,
**Gradle** и **CI-пайплайны** для обеспечения стабильности,
скорости и прозрачности разработки.

🔹 **Моя зона ответственности**
Я отвечал за **настройку и поддержку системы сборки на Gradle**,
а также участвовал в построении **полного CI-процесса**
— от коммита до проверки и сборки Docker-образов.

---

### ✅ **Gradle: как и зачем я использовал**

* Проект состоял из нескольких модулей (multi-module Gradle),
каждый из которых отвечал за свою подсистему (например,
`user-service`, `auth-service`, `core-lib`).

* С помощью **Gradle** я:

  * Настроил общий `build.gradle.kts` с зависимостями и версионированием.
  * Разделил зависимости на `implementation`, `api`, `testImplementation` для лучшего контроля.
  * Использовал **Gradle tasks** (`bootJar`, `test`, `jacocoTestReport`) в CI.
  * Настроил **version catalog (libs.versions.toml)** для унифицированного управления зависимостями.
  * Внедрил **checkstyle**, **SpotBugs**, **Jacoco** — всё интегрировалось в процесс сборки через Gradle плагины.

---

### ✅ **Continuous Integration (CI): зачем и как использовал**

* Настроил **CI на GitHub Actions**, чтобы каждый коммит в `main` и `feature/*` ветки автоматически проходил следующие стадии:

  1. **Сборка проекта (`./gradlew build`)**
  2. **Запуск юнит- и интеграционных тестов**
  3. **Анализ покрытия кода (`jacoco`)**
  4. **Проверка качества кода (`checkstyle`, `spotbugs`)**
  5. **Сборка и публикация Docker-образа (если тег релиза)**

---

### ✅ **Зачем это всё**

* **Ранняя проверка ошибок**: коммит не попадал в `main`, если что-то не проходило — это дисциплинировало команду.
* **Быстрая обратная связь**: при пуше в PR я уже через пару минут видел, упал ли билд.
* **Надёжные релизы**: мы делали релизы через GitHub Releases — CI собирал Docker-образ, проверял его и пушил в регистр только при успехе всех стадий.
* **Документируемость**: все процессы были автоматизированы, и любой разработчик видел, как устроен билд.

---

🔹 **Достижения**

* Сократил время сборки проекта с 6 до 3 минут за счёт кеширования и распараллеливания задач в Gradle.
* Внедрил CI-проверки в каждый PR — устранили типичные баги на ранних этапах.
* Упростил онбординг новых разработчиков: один `./gradlew build` запускал полный цикл локально так же, как и на CI.

🔹 **Технологии**

* Java 17+, Spring Boot 3
* Gradle (Kotlin DSL), JaCoCo, Checkstyle
* GitHub Actions, Docker, GitHub Container Registry
* Multi-module project setup, CI/CD pipelines
