Пример **легенды для интервью Java Backend разработчика**,
в которой рассказывается, **как и зачем он использовал
Docker при разработке микросервисов**:

🔹 **Контекст проекта**
Я работал над разработкой распределённой системы
на основе **микросервисной архитектуры**.
Каждый микросервис был самостоятельным Spring Boot приложением,
и все они взаимодействовали друг с другом через **REST и gRPC**.
Чтобы обеспечить стабильную разработку, тестирование и запуск
в разных средах, мы с командой активно использовали **Docker**.

---

### ✅ **Как я использовал Docker в работе**

* Каждому микросервису создавался собственный `Dockerfile`,
в котором я собирал минимальный образ:

  ```Dockerfile
  FROM eclipse-temurin:17-jdk-alpine
  COPY build/libs/app.jar app.jar
  ENTRYPOINT ["java", "-jar", "/app.jar"]
  ```
* Использовал **multi-stage сборку** для уменьшения размера образа.
* Все сервисы поднимались локально и на CI с помощью **Docker Compose**, включая:

  * PostgreSQL / Redis / Kafka
  * Jaeger / Prometheus / Grafana
  * Сами микросервисы

* Для быстрой локальной отладки и воспроизведения ошибок
я запускал связку `docker-compose up` и тестировал сразу весь стек,
включая взаимодействие между сервисами.

---

### ✅ **Зачем Docker был нужен**

* **Изоляция среды**: каждый сервис имел предсказуемое окружение — не зависел от установленных на машине разработчика библиотек или СУБД.
* **Быстрая разработка и тестирование**: благодаря Docker Compose я мог поднимать всю систему у себя локально, как на проде.
* **Упрощённый онбординг**: новый разработчик запускал `docker-compose up` и сразу мог работать с системой, не тратя часы на настройку окружения.
* **CI/CD**: на GitHub Actions у нас был процесс, который автоматически собирал Docker-образы после успешной сборки и тестов.

---

### ✅ **Интеграция с разработкой**

* Прописал в `docker-compose.yml` named volumes и сети, чтобы можно было "горячо" подключать исходники для отладки.
* Настроил `wait-for-it.sh` скрипты для контроля готовности зависимых сервисов (например, база данных).
* Использовал **Testcontainers** в автотестах, чтобы окружение для тестирования совпадало с Docker-окружением.

---

### ✅ **Результаты**

* Разработка стала **предсказуемой и одинаковой на всех машинах**.
* Мы легко развернули проект в Kubernetes — все Docker-образы уже были готовы.
* Минимизировали "работает у меня — не работает у тебя" ситуации.
