I. Lombok for Constructor Generation

The "Lombok Constructors and Field Injection Wisdom"
source details a practical application of Lombok to
automate constructor generation in Java classes.

Main Theme:
Automating boilerplate code for constructors using Lombok.

Key Ideas/Facts:

Target Classes:
The specific classes identified for constructor
generation are TravelCalculatePremiumServiceImpl
and TravelCalculatePremiumController.

Lombok Annotation:
The **@RequiredArgsConstructor(access = AccessLevel.PACKAGE)**
annotation is specified as the tool to achieve this.

Access Level:
The access = AccessLevel.PACKAGE parameter indicates
that the generated constructor will have package-private
visibility. This is a crucial detail for controlling
access to the constructor.

Final Fields:
A significant point is made regarding how Lombok handles
fields within the generated constructor: "PS: если вы хотите,
что бы Lombok добавил в параметр конструктора свойство класса
то при использовании
@RequiredArgsConstructor(access = AccessLevel.PACKAGE)
свойство класса должно быть final." This means that for
Lombok to include a class property as a parameter in the
generated constructor when using @RequiredArgsConstructor,
that property must be declared as final. This aligns with
the common practice of injecting dependencies through
constructors as final fields, ensuring their immutability
after construction.

Verification of Generated Code:
The source explicitly instructs users to verify the
generated code: "Обязательно загляните в одну из этих
папок после сборки проекта и посмотрите какой конструктор
будет добавлен в ваш класс." It provides the exact paths
for checking the generated bytecode:

out/production/classes (for IDEA projects)

build/classes (for Gradle projects)


II. The Case Against Field Injection

The instruction to "Прочитайте документ:
Oliver Drotbohm - Why field injection is evil.pdf"
highlights a critical architectural principle related
to dependency injection.

Main Theme:
The inherent problems and drawbacks of using field injection
as a dependency injection mechanism.

Key Idea/Fact:

"Why field injection is evil":
While the full content of Drotbohm's PDF is not provided,
the title itself, "Why field injection is evil," clearly
conveys a strong negative stance against field injection.
This implies that the document will likely detail various
reasons why field injection is considered an anti-pattern
in software development, particularly in the context of
frameworks like Spring where it is commonly
(and often mistakenly) used. Common arguments against
field injection include:

Reduced Testability:
Classes become harder to test in isolation without a
full Spring context.

Hidden Dependencies:
Dependencies are not explicitly declared in the constructor,
making a class's requirements less obvious.

Difficulty in Construction:
Without a default constructor or proper initialization,
constructing objects outside the framework can be problematic.

Violation of Single Responsibility Principle:
Encourages classes to have too many dependencies,
leading to larger, less focused classes.

Circular Dependencies: More difficult to detect and manage.

Connection to Lombok:

The inclusion of both topics suggests a best practice
approach: use Lombok to simplify the creation of
constructor-based dependency injection (which is generally preferred)
and avoid field injection (as argued by Drotbohm).
By using @RequiredArgsConstructor with final fields,
the developer is encouraged to adopt a robust and testable
form of dependency injection, moving away from the "evil"
practices of field injection.
