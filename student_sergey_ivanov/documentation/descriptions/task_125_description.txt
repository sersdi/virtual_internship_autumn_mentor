Задача: изучить семантические правила версионирования.

Семантическое версионирование (SemVer)—это стандарт, который говорит, как нумеровать версии
и что по номеру можно понять про изменения.
Его главная цель: чтобы по версии (1.2.3) сразу было ясно, безопасно ли обновляться и не сломается ли твой код.

Формат версии
Классическая версия SemVer выглядит как MAJOR.MINOR.PATCH (например, 2.4.1).

MAJOR (мажор, первое число)—меняют, когда есть breaking changes (изменения, ломающие обратную совместимость).
MINOR (минор, второе число)—добавили новую функциональность, но не ломая то, что работало раньше.
PATCH (патч, третье число)—исправили баги, сделали оптимизацию, но без новых публичных возможностей.
Пример: 1.0.4 → 1.1.0 (добавили фичу, совместимость сохранена) → 2.0.0 (сломали API, нужна адаптация кода).

Когда что увеличивать (с примерами для Java/Spring)

MAJOR (увеличить мажор)
Когда клиентский код перестанет работать без изменений.
Для Java‑проекта это, например:
Изменили сигнатуры публичных методов (тип возврата, набор аргументов).
Удалили публичный класс/метод, который кто‑то мог использовать.
Поменяли формат ответа REST API (удалили поле, изменили тип, структуру JSON).
Переименовали важные бины Spring, из‑за чего перестанет работать автоконфигурация.
Пример: было public int getAge(), стало public long getAge() и старые клиенты, ожидающие int, могут вести себя иначе (или это часть контракта API). Это повод для MAJOR.

MINOR (увеличить минор)
Добавили что‑то новое, но старое продолжает работать как раньше:

Новый эндпоинт в контроллере (новый REST‑метод).
Новый метод в публичном интерфейсе, который не ломает старые реализации.
Новая конфигурация/бин, который опционален и не обязателен для работы.
Поддержка нового формата данных параллельно со старым.
Пример для Spring Boot: добавили новый стартер my-app-starter-extra, но старый my-app-starter работает точно так же. Это MINOR.

PATCH (увеличить патч)
Исправления, которые не добавляют новых публичных возможностей и не ломают совместимость:

Исправили баг в логике.
Улучшили производительность внутри.
Исправили валидацию, чтобы она работала корректнее (но контракт остался тем же).
Мелкие правки документации, тестов, CI.
Пример: исправили ошибку валидации возраста, из‑за которой иногда пропускались некорректные значения. Это PATCH.

Особые случаи

До 1.0.0 (версии 0.x.y) SemVer разрешает любые breaking changes без увеличения мажора.
Это период активной разработки, когда API ещё не стабилизировался.

Предрелизные версии (например, 1.0.0-alpha, 1.0.0-rc.1)—это версии до стабильного релиза.
Они могут быть несовместимы между собой.

Метаданные сборки (например, +build.20251010)—идут после версии и не влияют на совместимость.
Их используют для однозначной идентификации сборки (CI, Docker‑теги и т.п.).

Как SemVer используют в Java‑экосистеме
Maven/Gradle зависимости: в pom.xml или build.gradle часто пишут диапазоны вроде ^1.2.3 или ~1.2.3. Символ ^ означает «можно обновлять до любой версии с тем же MAJOR», потому что SemVer обещает, что миноры и патчи обратно совместимы.
Spring Boot и другие фреймворки: строго следуют SemVer, чтобы библиотеки могли безопасно обновляться.
REST API: мажорную версию API часто выносят прямо в URL: /api/v1/orders и /api/v2/orders, чтобы чётко разделить несовместимые изменения.

SemVer помогает:
Понять, безопасно ли подтянуть новую версию библиотеки в проект.
Решить, нужно ли писать новые тесты под изменения API или достаточно старых.
Чётко обозначить, когда релиз требует миграции (например, обновления скриптов, миграции БД, изменения контрактов).
