Клиент принял решение установить разработанное
нами приложение на своей тестовой среде. Клиент просит нас подготовить
Fat Jar файл для нашего приложения. Fat Jar должен иметь
название insurance-calculator-1.0.0.jar и запускаться
командой из консольной строки:

Задача:

1. Разобраться в разных деплоймент артефактах: Thin Jar, Fat Jar, Thin War, Fat War.

2. Разобраться в командах Gradle предназначенных для создания деплоймент артефактов.

3. Разобраться с конфигурацией добавленной в build.gradle файл.

4. Сгенерировать требуемый деплоймент артефакт и протестировать его запуск.

5. Поэкспериментировать с созданием различных деплоймент артефактов:
Thin Jar, Fat Jar, Thin War, Fat War и изучить их внутреннюю структуру.


Решение:

1)
Это разные способы упаковки Java‑приложений.
Они определяют, какие зависимости попадают в итоговый артефакт.

Thin JAR
Что это: JAR‑файл, который содержит только классы приложения и самые прямые зависимости.
Всё остальное (библиотеки, фреймворки) должно быть предоставлено средой запуска (classpath, контейнер, сервер приложений).
Особенности:
маленький размер.
Не запускается командой java -jar без настройки classpath;
удобно для модульных архитектур и когда среда исполнения уже содержит нужные библиотеки.
Как собирают: обычно стандартным maven-jar-plugin или gradle jar без дополнительных плагинов для включения зависимостей.

Fat JAR (он же Uber JAR)
Что это: самодостаточный JAR, куда упакованы и твой код, и все зависимости (часто включая встроенный сервер, например Tomcat в Spring Boot).
Особенности:
большой размер.
запускается одной командой: java -jar myapp.jar;
очень популярен в микросервисах и в Spring Boot: плагин spring-boot-maven-plugin по умолчанию собирает именно Fat JAR.
Пример для Spring Boot: в Maven это поведение даёт spring-boot-maven-plugin, в Gradle—spring-boot-gradle-plugin.

Thin WAR
Что это: WAR‑архив, который содержит твой веб‑код (JSP, сервлеты, классы, ресурсы) и, возможно, некоторые библиотеки, но не содержит runtime‑компоненты сервера приложений (сервлет‑API, JSP‑движок и т.п.) — они уже есть в контейнере (Tomcat, Jetty, WildFly и др.).
Особенности:
рассчитан на деплой в полноценный Java EE / Jakarta EE сервер;
размер меньше, чем у Fat‑аналогов;
типичная модель для «классических» веб‑приложений.


Fat WAR
Термин «Fat WAR» используют реже, но смысл понятен: это WAR, куда дополнительно включены зависимости, которые обычно предоставляет сервер.
На практике так почти не делают, потому что:
серверы приложений ожидают «тонкие» WAR и сами управляют библиотеками;
включение runtime‑библиотек в WAR может вызвать конфликты версий и проблемы загрузки классов.
Вместо «Fat WAR» в современном стеке чаще используют либо Thin WAR для деплоя на Tomcat/Jetty, либо вообще уходят от WAR в сторону Fat JAR со встроенным сервером (как в Spring Boot).


Spring Boot по умолчанию делает Fat JAR.


2)
Базовые команды запуска задач (CLI)
./gradlew build — полная сборка: компиляция, тесты, создание JAR/WAR.
Это основной способ получить артефакт для деплоя.

./gradlew clean build — очистка старых артефактов и сборка заново.
Полезно перед публикацией или деплоем, чтобы не тащить старые файлы.

./gradlew assemble-только сборка артефактов (без тестов). Быстрее, если тесты уже прошли.


Задачи для JAR‑артефактов:
jar — создаёт обычный JAR (Thin JAR, если не настроен иначе).
В Spring Boot почти не используется напрямую, потому что нужен Fat JAR.

bootJar — создаёт Fat JAR для Spring Boot (самодостаточный, со встроенным Tomcat).
Это основная задача для микросервисов.

bootWar — создаёт Fat WAR (если проект на Spring Boot и настроен под WAR).

Артефакты обычно лежат в build/libs.


Задачи для WAR‑артефактов (классические веб‑приложения)

war—создаёт Thin WAR (без зависимостей runtime‑сервера).
Подходит для деплоя на отдельный Tomcat/Jetty.

bootWar (Spring Boot)—может делать WAR со встроенным контейнером или без него, в зависимости от конфигурации.
Если нужно явно собрать WAR:

publishToMavenLocal — публикует артефакт в локальный Maven‑репозиторий (~/.m2/repository).
Удобно для локальной проверки зависимостей.

publish — публикует во все настроенные репозитории (требует настройки publishing в build.gradle).

Специфика для Thin JAR под Docker (частый кейс для Spring Boot)
Чтобы делать Thin JAR и отдельно копировать зависимости (для маленьких и быстрых Docker‑образов),
используют dependency‑задачи:
copyDependencies (через maven-dependency-plugin аналог в Gradle)—копирует зависимости в отдельную папку.
В Gradle это делают кастомной задачей или плагином вроде com.github.johnrengelman.shadow либо просто задачей Copy.
